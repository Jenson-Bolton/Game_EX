## Executive summary

`v0.1.5` replaces window-only desktop shells with the first real graphics
vertical slice. `GameEX::Render` defines an ordinarily owned, backend-neutral
lifecycle for one validated linear-colour clear frame. `GameEX::RenderOpenGL`
creates and verifies an OpenGL 4.6 Core context through SDL, uses a core-4.6 GLAD
loader and validates every procedure this slice invokes, queries drawable pixels,
clears, checks API errors, and presents. Both the game and world editor use the same factory and exact
diagnostic colour `(0.035, 0.065, 0.110, 1.0)`.

The application startup graph now starts the renderer and presents the first
frame while the native window remains hidden. Only then does the dependent
visibility subsystem show it. Reverse shutdown hides the window before
releasing the graphics context, and ordinary member ownership destroys the
renderer before its borrowed window and SDL runtime. Fake-backed tests prove
this ordering and partial-start/runtime-failure cleanup independently of a GPU.

The final isolated workspace MSVC `/W4 /WX` build passed all 13/13 tests in 2.14
seconds. These include a real OpenGL smoke that reported OpenGL 4.6 Core,
`NVIDIA Corporation`, and `NVIDIA GeForce RTX 3060 Ti/PCIe/SSE2`, plus rendered
game and editor launches. A separately configured Engine build passed 7/7 tests
in 0.54 seconds. Strict warning-as-error Doxygen completed without warnings.

This is intentionally a clear/present and ownership result. It does not add
Vulkan, renderer CLI policy, shaders, meshes, resources, world-package loading,
terrain visualisation, editor UI, gameplay, or simulation. Those exclusions
prevent the first backend from inventing an untested RHI for the second.

## Scope and aim

The version asks whether one narrow rendering contract can be shared by game
and editor, exercised through a real OpenGL implementation, and remain suitable
for the required Vulkan backend. Accepted outcomes were:

- establish `GameEX::Render` without exposing SDL, OpenGL, or future Vulkan
  native types;
- create a presentation-capable window from a neutral factory requirement;
- use ordinary ownership rather than renderer globals, singletons, or a service
  locator;
- enforce single-use lifecycle states, creator-thread use, partial-start
  cleanup, and renderer-before-window destruction;
- start and successfully clear before the window becomes visible, then hide
  before graphics shutdown;
- require actual OpenGL 4.6 Core, double buffering, and sRGB presentation rather
  than treating requested attributes as evidence;
- load the exact needed API surface reproducibly without adding Python/Jinja to
  supported builds;
- validate every clear component as finite and within inclusive `[0, 1]`;
- query drawable pixels, set the viewport, clear, inspect `glGetError`, and swap
  for each frame;
- expose backend-neutral runtime diagnostics that Vulkan can fill later;
- prove contract logic with fakes and the concrete path with real GUI smokes;
- retain strict compilation, Doxygen, architecture, history, and dependency
  provenance evidence.

The explicit exclusions were equally important: no shaders, mesh abstraction,
GPU resources, command lists, world data, screenshot equality, editor widgets,
Vulkan implementation, or `--renderer` option.

## Design and implementation

### Targets and public boundary

`GameEX::Platform` is now an interface target for the abstract window/platform
headers. `GameEX::Render` depends on it and owns `Renderer`, `RendererFactory`,
`DiagnosticFrame`, neutral diagnostics, lifecycle states, categorized errors,
and stable backend names. `GameEX::RenderOpenGL` implements that API and keeps
its SDL, GLAD, and platform-bridge dependencies private. `GameEX::Core` consumes
only the shared interfaces. `GameEX::GameApp` is the composition root that links
the SDL platform and OpenGL backend for both executables.

`RendererDiagnostics` records backend, major/minor/patch API version, textual
profile, generic debug-diagnostics state, driver version text, vendor, and
device. It deliberately has no OpenGL-only boolean. `RendererBackend` names
actual implementations; application modes such as `auto` are not renderer
states. The lowercase `opengl`/`vulkan` text is fixed now for future logs and CLI
policy.

`WindowGraphicsApi` lets a factory declare `none`, `open_gl`, or `vulkan` before
native creation. The SDL adapter stores that value. A private checked bridge
uses the concrete runtime type and capability to return `SDL_Window*` only to a
backend implementation. Public headers never contain SDL/GL handles or `void*`.

### Lifecycle and failure behavior

The OpenGL renderer moves through dormant, starting, running, stopping, stopped,
and failed states. A normal start is permitted only from dormant and restart is
not supported. Any start exception records failed before propagating; shutdown
accepts running or failed so the startup graph can roll back an allocated but
incomplete context. Explicit misuse raises `RendererError` with a stable code.

The creator thread owns all SDL/OpenGL operations. A foreign call is rejected;
foreign destruction fails fast because silently destroying an SDL context on
another thread would violate the backend contract. The state observer is atomic
and non-throwing, but that does not grant cross-thread mutation rights.

Application copies the requested window specification, applies the factory's
required graphics API, creates the hidden window and dormant renderer, validates
the factory result, and registers two main-thread-affine subsystems:

```text
render.backend --> platform.window.visibility
```

The renderer subsystem starts and presents the shared frame. The visibility
subsystem then shows the window. The loop pumps events, presents the same frame,
and applies the existing short pacing sleep. Runtime exceptions trigger graph
shutdown; reverse order hides before renderer shutdown. The startup graph itself
handles a failing renderer subsystem, including its partially started object.

### OpenGL contract

Before window creation SDL attributes request OpenGL 4.6, Core profile, double
buffering, an sRGB-capable default framebuffer, and eight-bit RGBA channels.
Startup creates/makes current the context and loads GLAD from SDL's procedure
resolver. GLAD confirms a context advertising 4.6, after which the backend
explicitly checks every function pointer it will invoke; it does not claim all
generated 4.6 pointers are non-null. It rejects an actual version below 4.6, a
non-Core profile, missing diagnostic strings, an unavailable double buffer, or a
non-sRGB framebuffer. It enables and verifies `GL_FRAMEBUFFER_SRGB`, preserving
the public promise that the clear components are linear values encoded for the
display framebuffer.

Each frame re-establishes the context, obtains pixel rather than logical-window
dimensions, accepts a zero extent but rejects negative/failed queries, sets the
viewport, clears the colour buffer, checks the GL error state, and swaps the SDL
window. No API state beyond that operation is implied.

### Reproducible GLAD intake

The source archive is the official GLAD `v2.0.8` tag archive at
`https://github.com/Dav1dde/glad/archive/refs/tags/v2.0.8.tar.gz`, 645,593 bytes,
with SHA-256
`44F06F9195427C7017F5028D0894F57EB216B0A8F7C4EDA7CE883732AEB2D0FC`.
Generation used GLAD 2.0.8, Jinja2 3.1.6, and MarkupSafe 3.0.2 with:

```text
--api gl:core=4.6 --extensions '' --out-path <output> --reproducible c
```

No internal loader, aliases, debug wrapper, multi-context mode, on-demand mode,
or extension was selected. Because the generator follows host newline
conventions, its text outputs are normalized to UTF-8 without a byte-order mark
and LF line endings before hashing. Only those normalized generated outputs and
the exact LF upstream licensing content are supported source inputs:

| File | SHA-256 |
| --- | --- |
| `include/glad/gl.h` | `0E1AC72E82AEC8AB8D1FE176E46A471643C9673B03BA42C4DF6DEA89D2F0E7F5` |
| `include/KHR/khrplatform.h` | `7B1E01AAA7AD8F6FC34B5C7BDF79EBF5189BB09E2C4D2E79FC5D350623D11E83` |
| `src/gl.c` | `07CF9E52E7C018A1E5A8FDE75BFE63F0527B3963B9F5F6219AE04924FBE934C1` |
| `LICENSE` | `CBB325CD4AC5BD06717FFA34A322B984F9D285E4C67C8CA1B7380D6EF08C2A77` |

CMake verifies the three generated hashes at configure time, Git attributes pin
all vendored files to LF, exempt the generated C/headers from project whitespace
rewrites or checks, and Doxygen excludes third-party code. This preserves every
generator-authored character other than newline encoding. GLAD generator source
is MIT-licensed. Generated `gl.h`/`gl.c` carry
`(WTFPL OR CC0-1.0) AND Apache-2.0`; `khrplatform.h` retains its separate
Khronos permission notice. The vendor README preserves this distinction.

## Evidence and method

The isolated full-workspace verification used CMake 4.2.3, Visual Studio
2022/MSVC 19.44.35224, Windows SDK 10.0.26100, SDL 3.4.14, and the repository's
warning-as-error settings. The already verified SDL source was supplied to the
fresh build only to avoid another network fetch:

```powershell
cmake -S . -B .\build\v015 -G "Visual Studio 17 2022" -A x64 `
  -DFETCHCONTENT_SOURCE_DIR_SDL3="C:\dev\Game_EX\build\vs2022\_deps\sdl3-src" `
  -DGAMEEX_BUILD_DOCUMENTATION=ON -DGAMEEX_ENABLE_GUI_SMOKE_TESTS=ON
cmake --build .\build\v015 --config Debug --parallel 4
ctest --test-dir .\build\v015 -C Debug --output-on-failure
cmake --build .\build\v015 --config Debug --target docs --parallel 2
```

All 13/13 tests passed in 2.14 seconds. The nine unit-labelled modes include
JobSystem/StartupGraph regressions plus `engine.render_api` and
`engine.application_render_lifecycle`. Three GUI smokes took 1.55 seconds in
aggregate: the concrete backend, game, and world editor. The remaining tests
cover the unchanged WorldFormat/WorldCompiler integration.

Verbose backend evidence reported:

```text
OpenGL 4.6 core | NVIDIA Corporation | NVIDIA GeForce RTX 3060 Ti/PCIe/SSE2
```

Both applications reported `Selected renderer: opengl`, ran through the same
`GameEX::GameApp` composition, presented for the 250 ms automation interval,
and exited successfully.

Independent Engine configuration removed any reliance on Game or WorldCompiler:

```powershell
cmake -S .\Engine -B .\build\v015-engine -G "Visual Studio 17 2022" -A x64 `
  -DFETCHCONTENT_SOURCE_DIR_SDL3="C:\dev\Game_EX\build\vs2022\_deps\sdl3-src" `
  -DBUILD_TESTING=ON -DGAMEEX_ENABLE_GUI_SMOKE_TESTS=ON
cmake --build .\build\v015-engine --config Debug --parallel 4
ctest --test-dir .\build\v015-engine -C Debug --output-on-failure
```

That MSVC `/W4 /WX` build passed 7/7 tests in 0.54 seconds, including the real
OpenGL smoke. A separate GUI-off Engine configuration registered and passed the
six non-GUI test modes, proving `GAMEEX_ENABLE_GUI_SMOKE_TESTS=OFF` does not
leave a hidden GUI CTest requirement. Strict Doxygen excludes only audited
third-party files and completed with project-authored public, private, test, and
anonymous-namespace symbols warning-clean.

## Test design

Backend-neutral tests fix both the exact shared diagnostic colour and validation
of every channel at zero, one, just outside the range, infinity, negative
infinity, and NaN. They also fix lowercase backend names and error category
retention.

Fake Platform, Window, RendererFactory, and Renderer objects provide a complete
ordered trace without graphics or timing. The success case proves native
capability propagation, renderer start, first frame, show, loop frame, hide,
renderer shutdown, renderer destruction, window destruction, and platform
destruction. Injected failures prove that failed start and failed first frame
invoke partial-renderer rollback without showing the window, while a later frame
failure hides before shutdown. Null window/renderer results,
wrong-backend factory results, and a conflicting window capability fail during
composition before an unsafe dereference or startup.

The real smoke proves dormant/running/stopped transitions, rejects render before
start and repeated shutdown, rejects a NaN frame, queries real diagnostics,
clears while hidden, shows, clears again, pumps events, hides, and shuts down.
Game/editor smokes then prove the production composition caller rather than only
the backend fixture.

## Data, assets, and external dependencies

No world data, imagery, model, texture, shader, or other content asset enters
this release. The synthetic WorldCompiler fixture and `.gexworld` format remain
unchanged from `v0.1.4`; neither application reads it yet.

SDL 3.4.14 remains the pinned source dependency already accepted by the
foundation. GLAD 2.0.8 is the only new external dependency input and is fully
described above. The temporary Python/Jinja environment reproduced the same
generated text after the documented LF normalization, but is neither committed
nor invoked by CMake. No Vulkan SDK dependency is introduced in this version.

## Discussion and reflection

The most important design choice was to make the first shared Render API smaller
than a conventional RHI. Clearing and presenting is enough to test native window
flags, context ownership, function loading, framebuffer colour semantics,
drawable sizing, error propagation, startup rollback, and real application
composition. It is not enough evidence to choose resource handles, descriptor
models, shader layouts, synchronization, or render extraction. Leaving those
out reduces the chance that OpenGL terminology becomes a permanent burden on
Vulkan.

Presenting once while hidden turns visibility into a meaningful dependency
rather than a cosmetic ordering rule. A machine that cannot create the required
context never flashes an unusable application window. Treating the failing
renderer as shutdown-capable also uses the startup graph's partial-object
contract rather than relying on backend destructors alone.

The sRGB requirement closes a subtle semantic gap. Values called “linear” are
not made correct merely by passing floats to `glClearColor`; the presentation
target and conversion state matter. Requesting, querying, and enabling the
capability makes the documented frame meaningful for later Vulkan parity.

Vendoring generated loader code is an exception, but a bounded and auditable
one. It trades three hash-checked generated files for a Python/Jinja dependency
on every developer and build machine. Pinning EOL behavior matters because a
content hash that changes under Git checkout would provide false reproducibility.

## Limitations and risks

- Vulkan 1.3, explicit/automatic renderer selection, explicit no-fallback tests,
  and cross-backend parity remain unimplemented.
- The frame contains only a clear colour. It cannot validate shader compilation,
  geometry orientation, depth, resource lifetime, synchronization, texture
  colour space, or world coordinate precision.
- Smoke tests prove successful API work and swap, not captured pixel values or
  perceptual equality. Display capture will need a defined tolerance and cannot
  rely on cross-driver byte equality.
- GLAD uses process-global OpenGL function pointers. The current SDL platform
  deliberately owns one window/context, so multi-context behavior is not yet a
  supported claim.
- The backend requires OpenGL 4.6 Core and a double-buffered sRGB framebuffer;
  macOS's native OpenGL ceiling and older/headless drivers do not satisfy it.
- No swap interval, frame scheduler, minimized-window deferral, device-reset
  recovery, debug callback, profiling, or performance target is specified.
- Wrong-thread OpenGL destruction is enforced by inspection/fail-fast code but
  does not add another subprocess death test in this slice; existing owner-thread
  graph/job death tests and fake lifecycle coverage remain the proportional
  automated boundary.
- Only the supported Windows/MSVC/NVIDIA environment was executed. Non-MSVC
  warning policies and another GPU vendor still need CI evidence.
- Game and editor do not read or visualise `.gexworld`; the renderer proves
  technology and lifetime only.

## Next version

`v0.1.6` should implement Vulkan 1.3 behind `GameEX::Render`, add explicit
`--renderer=opengl|vulkan|auto` parsing and no-silent-fallback tests, and present
the same exact diagnostic clear through both paths. It should retain native SDL
surface integration privately, add Vulkan-specific validation without leaking
API types, and report comparable neutral diagnostics.

Only after that parity proof should the renderer API grow for the smallest
shared terrain view. The editor can then load one `.gexworld` package through
`GameEX::WorldFormat` and visualise heights and validity as separate data before
any source combination. Real DMR/TESSERA work remains behind the already
documented provenance and WorldCompiler repository-split gates.
