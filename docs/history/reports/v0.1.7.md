## Executive summary

`v0.1.7` connects the existing runtime world-package contract to the standalone
world editor. Supplying `--world=<path.gexworld>` causes the editor to open,
verify, and decode the package before it creates a graphics platform or window.
The terrain height and validity samples become an owning, bounded diagnostic
raster which the same neutral Render API presents through explicit OpenGL 4.6
Core and Vulkan 1.3 implementations.

This is an inspection tool rather than a terrain renderer. Valid heights use a
documented linear blue-green-yellow scale; invalid samples are vivid magenta;
the package's row zero remains at the lower edge and positive Y points upward.
The view retains the grid-cell sample-footprint aspect and letterboxes instead
of stretching. Inputs
larger than 64 x 64 are deterministically reduced to a display-only overview;
the package is never rewritten.

The implementation remains intentionally shaderless. OpenGL uses scissored
clears. Vulkan adds the core 1.3 dynamic-rendering feature, transactional
swapchain image views, a background load clear, and rectangular attachment
clears. This proves real package-to-pixel command flow without yet selecting
shader compilation, SPIR-V publication, textures, descriptors, pipelines,
camera interaction, or a general render-hardware interface.

## Aim and acceptance criteria

The question for this version was: can the world editor load the portable world
contract and visibly inspect height and validity through both real graphics
technologies without weakening repository or application boundaries?

Accepted outcomes were:

- keep `.gexworld` reading in an editor-only application target;
- load and map a requested package before platform/window/renderer startup;
- retain a no-world diagnostic editor shell;
- keep the game executable free of editor implementation and compiler code;
- keep both applications independent of `GameEX::WorldCompilerCore`;
- add an owning backend-neutral raster with strict finite and size validation;
- preserve row-major package orientation with row zero at the lower edge;
- preserve the half-cell-padded sample-footprint aspect with deterministic
  integer letterboxing;
- show valid height, invalidity, and partial validity with an explicit mapping;
- deterministically reduce larger rasters to at most 64 x 64 cells;
- implement the same frame semantics in OpenGL and Vulkan without shaders;
- retain typed deferral, terminal native-frame failures, strict selection, and
  fresh automatic fallback;
- compile the project-authored staging fixture to test-owned output rather than
  committing or overwriting an opaque generated package;
- add unit, integration, real backend, validation, boundary, Doxygen, and
  per-version documentation evidence.

Explicit exclusions were real geographic data, source adapters, TESSERA,
multiple layers, layer combination, quantitative picking, pan/zoom, 3D terrain,
gameplay, and final asset/resource abstractions.

## Design and implementation

### Render-frame contract

`DiagnosticFrame` remains one finite linear RGBA colour. `RenderFrame` owns a
background and an optional `DiagnosticRaster`. A raster owns its row-major colour
vector, logical dimensions, and intended display width/height ratio. Each
dimension is in `[1, 64]`, total cells cannot exceed 4,096, colour count must
exactly equal rows times columns, aspect must be finite and positive, and every
colour component remains in `[0, 1]`.

Owning data is important: the same immutable frame must survive the startup
graph's hidden attempt, the visible loop, and a second completely fresh
Platform/Application if automatic Vulkan selection qualifies for OpenGL
fallback. `RunConfiguration` owns that frame; no editor vector is borrowed by a
renderer. Public validation occurs before any native frame call.

Neutral diagnostics record the dimensions and cell count of the most recently
presented raster as well as the existing presentation count and validation
errors. A clear-only game frame reports zero raster dimensions.

### Shared pixel layout

One private Render helper converts a validated raster and current drawable size
into bottom-origin integer rectangles. It fits the declared display aspect
inside the complete drawable and centres any letterbox. Floor-partitioned
boundaries cover each content pixel exactly once without gaps or overlaps;
64-bit products prevent narrow intermediate overflow. Very small drawables may
produce zero-area logical cells, which native paths safely skip or clear as a
no-op while still preserving bounded layout.

The shared convention is left-to-right columns and row zero at the bottom.
OpenGL consumes those coordinates directly. Vulkan converts only the rectangle
Y coordinate to its top-origin framebuffer convention. This keeps package +Y
visually upward under both APIs.

For this colour-cell view, the declared display aspect is the grid's
half-cell-padded sample footprint: `columns * spacing_x` by
`rows * spacing_y`. In the conceptual unreduced grid, each source sample owns a
cell centred on it and the outer cells extend half a spacing beyond the outer
centres. Reduced display cells summarize complete source partitions while
retaining that full footprint. This is distinct from the WorldFormat numeric
bounds between the first and last sample centres, `(dimension - 1) * spacing`;
no package coordinate or bound is changed.

### OpenGL path

The OpenGL backend clears the entire verified sRGB default framebuffer to the
frame background with scissor disabled. For a raster it enables
`GL_SCISSOR_TEST`, applies the shared rectangle for each row-major colour, and
uses `glClearColor`/`glClear` for the cell. It disables scissor before checking
API state and swapping. The required-procedure audit includes the enable,
disable, scissor, clear, query, and presentation calls used by this path.

No vertex array, shader, buffer, texture, or sampler is introduced. Linear clear
values retain the existing framebuffer-sRGB intent.

### Vulkan path

Device suitability now requires both Vulkan 1.3 `synchronization2` and
`dynamicRendering`, FIFO, the existing sRGB choices, graphics/presentation
queues, transfer-destination plus colour-attachment surface usage, and matching
optimal-format features. Device creation explicitly enables both 1.3 features.

Each transactional swapchain generation owns its images, one colour image view
per image, layout history, and one presentation-wait semaphore per image. A
partial replacement destroys views before its new swapchain and never becomes
active. Successful replacement destroys old views before old presentation
semaphores and the old swapchain. Shutdown follows the same dependency order.

Frames without a raster retain the transfer-clear path from `v0.1.6`. Raster
frames transition the acquired image to colour-attachment layout, begin dynamic
rendering with a full-frame background load clear, issue one
`vkCmdClearAttachments` rectangle for each non-empty cell, end rendering, and
transition to presentation. The acquire semaphore is waited at the first
colour-attachment-output stage for this path. Submission, per-image presentation
semaphores, deferral, terminal error, validation, and presentation-count rules
remain unchanged.

### Editor-only composition

The editor has its own application/model target. It alone links the runtime
WorldFormat reader and terrain-to-raster interpretation. The player-facing game
uses the shared desktop runner with `foundation_render_frame()` and does not link
the editor target. Neither executable links the offline compiler core.

The editor first separates its optional `--world=` argument from the shared
renderer/timer arguments. Empty and repeated world options fail. With a path,
`read_world_package()` completes integrity/version/structure checks, then the
terrain mapper builds an owning frame and writes a reproducibility summary. Only
after that succeeds does the common runner print a renderer attempt or construct
SDL. Therefore a bad package cannot authorize renderer fallback.

The summary includes package format/checksum/path; terrain layer/tile; source
and displayed dimensions; valid/invalid counts; local and absolute height
ranges; EPSG, origin, spacing and aspect; provider/product/edition; source/stage
classification; attribution; colour mapping, aggregation and row orientation.

### Height, validity, and reduction

Global minimum/maximum use valid source samples only. A normalized height in
`[0, 0.5]` interpolates blue to green; `[0.5, 1]` interpolates green to yellow.
A globally flat valid field uses `0.5`. A bin with no valid samples is opaque
magenta. A partially valid bin uses the valid sample mean and blends its height
colour toward magenta by the invalid fraction.

Output columns and rows are independently `min(source dimension, 64)`. For each
axis, boundary `i` is `floor(i * source / output)`. The resulting Cartesian bins
are complete, non-overlapping, and deterministic. Valid heights are accumulated
as double and averaged; normalization still uses the global valid source range.
This is a derived in-memory overview only.

For the committed 2 x 2 fixture the intended layout is:

```text
top (+Y):     invalid | 4.0
bottom:           0.0 | 1.5
```

## Test design

Render tests cover frame/raster dimensions, exact storage, finite positive
aspect, cell colour validation, and the unchanged foundation colour. Layout
tests cover landscape/portrait aspect fitting, odd-pixel letterbox allocation,
complete partition coverage, row order, zero-area cells, and invalid inputs.
Fake Application tests prove the exact owned raster reaches hidden and visible
attempts while retaining lifecycle/failure behavior.

Editor model tests cover option extraction/order/error cases, exact 2 x 2
orientation and colours, flat/all-invalid fields, partial-validity blending,
sample-footprint aspect, logging, and a deterministic 251 x 201 to 64 x 64
reduction.
The application-boundary test supplies a missing/corrupt package and proves
failure occurs before the renderer-attempt marker.

CTest compiles the existing text fixture with the real offline compiler into a
test-owned `.gexworld`, then explicit OpenGL and Vulkan world-editor smokes load
that package. A separate shell smoke retains the no-world editor. The OpenGL
backend smoke presents a 3 x 2 raster and the Vulkan smoke presents a 2 x 2
raster; both assert neutral raster diagnostics. The
required Vulkan validation batch retains repeated presentation and zero-error
acceptance.

## Data, assets, and provenance

No external terrain, imagery, vector, texture, shader, model, or machine-learning
asset is added in this version. The only visualized package is compiled during
testing from the project-authored synthetic fixture under
`WorldCompiler/tests/fixtures/minimal`. Its manifest explicitly identifies it as
synthetic and records the project attribution, byte sizes, hashes, coordinate
contract, and transformation description already accepted in `v0.1.4`.

Generated test packages remain under ignored build output. No generated
`.gexworld`, raw DMR, TESSERA embedding, compiler dependency, or licence claim is
smuggled into source control. SDL3, GLAD, the Vulkan SDK, loader, and driver retain
their previously documented roles.

## Discussion and reflection

The shaderless raster is deliberately modest but answers a real integration
question: verified world bytes now influence commands submitted by both graphics
APIs through one immutable neutral input. Package errors, renderer selection,
native ownership, and editor/game linkage remain independently testable.

Aspect and orientation deserved explicit policies. A colourful 2 x 2 image can
look plausible while being transposed, vertically inverted, stretched, or based
on invalid values. Shared bottom-origin layout, exact expected fixture colours,
sample-footprint aspect, and logs make those errors observable before real
geography makes them harder to isolate.

The 64 x 64 bound is also an honest performance boundary. Thousands of clear
commands are acceptable for a diagnostic overview; treating that as a scalable
raster renderer would be misleading. The raster-shaped input allows backend
internals to move to one upload/full-screen draw later without changing world
interpretation, but no claim is made until that path is designed and tested.

## Limitations and risks

- The view is 2D, static, and non-interactive; there is no cursor readout,
  legend UI, zoom, pan, camera, geometry, or depth.
- Large sources are reduced to at most 4,096 display bins and cannot be inspected
  at original sample resolution.
- Per-cell native clear commands are not a production rendering strategy.
- There is one terrain tile and one layer; no source combination or precedence
  is exercised.
- The colour ramp is diagnostic, not a cartographic or accessibility standard.
- Automated tests prove command execution, semantic inputs, diagnostics, and
  validation, not captured-pixel equality.
- Vulkan still has the unextended WSI retirement limitation documented in
  `v0.1.6`.
- Runtime graphics evidence remains Windows/MSVC/NVIDIA only.
- A navigable 3D interpretation remains a project-owner specification choice.

## Next version

Before adding specialised geospatial or ML tooling to the supported source tree,
resolve the WorldCompiler repository split gate. The next real-data slice should
acquire and hash one official BYSH62 DMR5G source, record its feed/licence/CRS and
vertical datum, derive a deterministic validity-aware overview, compile it
through the same `.gexstage`/`.gexworld` boundary, and inspect it separately in
this editor.

Full-resolution rasters, multiple layers, interactive navigation, or a TESSERA
semantic overlay require the scalable upload/shader path described by ADR 0012.
The agreed first semantic proof remains a 2024 TESSERA region with four material
probabilities, compared separately before authoritative reconciliation.
