## Executive summary

`v0.1.3` adds controlled concurrency without weakening the deterministic lifecycle established in `v0.1.2`. `GameEX::Jobs` owns a bounded fixed worker pool and exposes only synchronous input-indexed batches. `StartupGraph` can now run explicitly eligible ready nodes concurrently while native/main-affine nodes remain on the application thread. All in-flight work settles at a barrier; logical admission order—not physical completion—selects results, the primary failure, commit order, and reverse rollback. The production application uses this path and owns the pool as serial bootstrap infrastructure. A strict MSVC build, seven workspace tests, four standalone Engine tests, and Doxygen verify the slice. It deliberately does not claim a general asynchronous frame scheduler.

## Scope and aim

The version asks whether independent startup work can use multiple cores while retaining reproducible dependency, failure, and cleanup semantics. Accepted outcomes are:

- an ordinarily owned fixed worker pool with a hard 1–32 bound and conservative default;
- a synchronous batch API with no unbounded queue, detached work, or escaping task lifetime;
- strong validation and preparation before jobs become visible to workers;
- results and exceptions retained by immutable input index after every accepted job settles;
- creator-thread and single-batch lifecycle protection, explicit shutdown, and destructor/partial-constructor joining;
- startup affinity that defaults to `main_thread`, with an opt-in `worker_eligible` class;
- full graph validation before side effects, bounded lexical admission, dependency barriers, deterministic failure selection, no later admission after failure, and serial owner-thread reverse rollback;
- preservation of the original serial startup path;
- production Application integration, focused unit tests, strict compilation, and full Doxygen.

Priorities, cancellation, work stealing, futures, arbitrary nested/concurrent submission, dynamic resizing, frame scheduling, rendering, compiler ingestion, and world data are excluded.

## Design and implementation

`JobSystem` creates an immutable number of persistent workers. Configuration rejects zero and values above 32. The default leaves one reported logical processor for the application when possible, clamps to one through eight workers, and avoids unsigned underflow for unknown/single-core reports. The control thread submits at most one worker-count-sized batch and blocks until a `std::latch` records every result. Jobs and exception slots are allocated before publication; workers claim indices under a mutex and write only their own result slot. Job exceptions never escape worker threads.

Only the creator thread may submit, explicitly shut down, or destroy the pool and graph. Nested worker submission and foreign/concurrent control calls therefore fail rather than deadlock. Wrong-thread destruction ends the process immediately with failure before affinity-sensitive cleanup or worker joining begins. Correct-thread shutdown/destruction stops admission and joins all threads; partial constructor failure also joins every successfully created worker.

Controlled startup retains a sorted ready set. If its first stable ID is main-affine, that one node runs on the graph owner and readiness is recomputed. Otherwise, the maximal leading worker-eligible prefix—capped by pool size—is admitted as an indexed batch. The graph waits for every callback, records all attempted nodes in admission order, chooses the lowest-index exception, and admits nothing later on failure. Cleanup then runs serially on the owner in reverse logical admission. Reserving the entire rollback ledger before callbacks ensures recording a settled batch cannot allocate after side effects.

`Application` owns `JobSystem` before `StartupGraph`, calls the controlled overload, and declares window visibility `main_thread`. This proves the path while ensuring graph shutdown precedes worker joining and native window destruction. [ADR 0008](../../decisions/0008-bounded-jobs-controlled-parallel-startup.md) is the durable contract.

## Evidence and method

The release is checked with a fresh Visual Studio 2022 x64 build using MSVC 19.44 and Engine `/W4 /WX`:

```powershell
cmake --preset vs2022
cmake --build --preset debug
ctest --preset debug --output-on-failure
cmake --build --preset docs
```

Concurrency tests use explicit worker counts and `std::barrier`, `std::latch`, and atomic gates. This proves simultaneous execution, wait semantics, and an inverted failure-point order without treating elapsed time or scheduler luck as correctness evidence.

The final workspace run passed 7/7 tests in 0.81 seconds: the normal and wrong-thread-destruction modes for `engine.job_system` and `engine.startup_graph`, plus `world_format.header`, `game.window_smoke`, and `world_editor.window_smoke`. A separate Engine-only configure/build passed all 4/4 Engine tests in 0.12 seconds. Both normal concurrency suites then passed 100 consecutive repetitions each (200 test invocations) in 1.93 seconds. Strict Doxygen completed without warnings and covers the new public, implementation, and test C++ files. The rebuilt compiler reported application version `0.1.3` and the separately versioned placeholder world-format contract remained `0.1`.

## Discussion and reflection

The narrow batch API intentionally trades throughput flexibility for a small observable contract. It is sufficient for startup preparation while avoiding promises about detached lifetime, cancellation, continuations, or frame latency. The key distinction is that physical concurrency is allowed to vary but state-transition decisions are not.

Waiting for a failed batch before rollback is essential. Returning on the first wall-clock exception would allow cleanup to race another subsystem still acquiring resources. Similarly, picking the earliest observed exception would make diagnostics machine-load dependent. Indexed outcomes make both issues explicit.

The job pool is bootstrap infrastructure rather than a graph node because scheduling its own creation would be circular. Ordinary Application ownership keeps that exception local and visible.

## Limitations and risks

- Barrier scheduling can leave workers idle and is not a performance model for per-frame jobs.
- `std::function` copies and shared batch state are appropriate for small startup workloads but have not been benchmarked.
- Worker callbacks can still perform inherently order-sensitive external side effects; the API only makes Game_EX's commit/failure bookkeeping deterministic.
- Cleanup failures during startup rollback remain secondary to the primary startup exception and need a future diagnostic aggregation channel.
- There is no public worker-count configuration yet; the application uses the conservative hardware recommendation.
- Wrong-thread destruction is intentionally unrecoverable; dedicated CTest death modes verify the non-zero process exit, but no cleanup or diagnostic aggregation can occur after this contract violation.
- Rendering, compiler, and data paths have not yet exercised eligible production subsystems.

## Next version

The next patch should implement the portable WorldCompiler staging contract before adding any heavyweight geospatial dependencies: explicit source/provenance metadata, deterministic validation, an independently readable layer package, safe little-endian reader/writer code, and useful `inspect`/`validate`/`compile` commands. The compiler repository split gate remains mandatory before GDAL, PROJ, supported Python/network acquisition, or ML tooling enters the build.
