## Executive summary

`v0.1.1` turns releases into explicit evidence-backed project records. It adds a working agreement, a chronological report index, a reusable technical-report structure, a retrospective foundation report, and one centrally propagated project version for the workspace and its constituent projects. It also records the owner's requirement for OpenGL and Vulkan renderer backends behind one shared Render API. All three existing CTest checks passed, strict Doxygen generation succeeded, and the compiler reported the propagated `0.1.1` application version while retaining the separate world-format `0.1` value. The change is intentionally administrative and build-facing: it removes version drift and defines how later compiler, real-data, and editor work will be specified, verified, documented, tagged, and published. It does not claim a new world-data or visualisation capability.

## Scope and aim

The version addresses two weaknesses found after the foundation push: release evidence had no durable per-version home, and version numbers were declared independently. Its accepted outcomes are:

- a concise root explanation of how work progresses;
- an enforceable working agreement with specification gates and a definition of done;
- one technical report per SemVer release and a chronological index;
- a transparent bootstrap report for `v0.1.0` without rewriting Git history;
- a single version definition propagated consistently to Engine, WorldCompiler, Game, and application/compiler metadata;
- an updated changelog and release traceability;
- an accepted architecture decision requiring separate OpenGL and Vulkan backends behind one shared rendering boundary.

The required backend set is selected by ADR 0004. Renderer implementation, runtime backend-selection policy, real-world data import, world compilation, and editor visualisation remain outside this version.

## Design and implementation

The workflow treats a version as one coherent unit: agreed scope, implementation, tests, Doxygen, human documentation, provenance where applicable, changelog, report, release commit, annotated tag, and GitHub publication. Decisions with long-lived architectural, data, licensing, or format consequences stop at a specification gate rather than being embedded silently in code.

Reports use the structure of a technical coursework report—aim, design/implementation, evidence, results, data/assets, discussion/reflection, limitations, and next work—but remain version-controlled Markdown close to the implementation evidence. Generated Doxygen remains the authoritative code-level reference; reports link to it conceptually and do not duplicate API descriptions.

The build change centralises `GAMEEX_VERSION` in `cmake/GameEXVersion.cmake`. The root, Engine, WorldCompiler, and Game projects include that authority before their `project()` declarations. The `gameex_apply_version(target)` helper supplies `GAMEEX_VERSION_STRING` only to targets that expose the application version: `gameex_game_app` passes it to the shared SDL desktop metadata, and `game_ex_world_compiler` uses it in its banner. The world-format version remains an independent compatibility value.

[ADR 0004](../../decisions/0004-dual-renderer-backends.md) records the cross-technology rendering requirement. The game and editor will use one backend-neutral Render API, while OpenGL, Vulkan, and the necessary SDL presentation integration remain private implementation targets. Exact API baselines, backend selection, fallback, and release-by-release parity are left for owner confirmation before implementation.

## Evidence and method

The release was checked with:

```powershell
cmake --preset vs2022
cmake --build --preset debug
ctest --preset debug
cmake --build --preset docs
```

Configuration and the Debug build completed successfully with MSVC `/W4 /WX`. CTest passed three of three tests—`world_format.header`, `game.window_smoke`, and `world_editor.window_smoke`—in 0.68 seconds. The strict Doxygen target completed successfully. A separate Game-project configure and build also succeeded, exercising its standalone composition of the sibling Engine and WorldCompiler projects. Running the compiler produced:

```text
Game_EX World Compiler 0.1.1 foundation (world format 0.1)
No world compilation pipeline is configured yet.
```

The second line confirms that no compilation pipeline has yet been configured. This separates the application version from the world-format compatibility version and avoids presenting the placeholder as a compiler implementation. The annotated tag is the canonical immutable release reference.

## Data and assets

This version introduces no world dataset or project asset. It changes project process, documentation, and version metadata only. The existing pinned SDL3 dependency is unchanged.

## Discussion and reflection

The report system makes limitations and provenance part of acceptance rather than optional notes added after a feature. The bootstrap exception is important: preserving the original foundation commit gives a more trustworthy history than amending it to appear compliant with a policy written later.

Central version propagation reduces a small but compounding maintenance risk. It also gives compiler outputs and future runtime compatibility checks one release identity, provided generated metadata never becomes a substitute for an explicit world-format version.

## Limitations and risks

- The workflow relies on review discipline; automated checks should later verify that version declarations, changelog, report, and tag agree.
- A Game_EX application version and a persistent world-format version describe different compatibility promises and must not be conflated.
- Markdown reports preserve evidence links but do not capture command logs automatically.
- This version does not decide how geographic layers are rendered, combined, licensed, or packaged.
- OpenGL/Vulkan minimum versions, backend selection and fallback, and feature-parity timing still require owner confirmation.

## Next version

The next patch should implement the previously agreed serial startup graph with validation, deterministic ordering, reverse shutdown, and partial-start rollback. The following patch can add the job system and controlled parallel scheduling. After those lifecycle foundations, separately reported patches should establish the staging world format/compiler, attributed Czech Republic data, the shared Render API with both graphics backends, and the editor viewer before `v0.2.0` summarises the integrated capability.
