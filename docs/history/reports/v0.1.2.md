## Executive summary

`v0.1.2` establishes the first reusable engine lifecycle subsystem instead of extending the restart through global managers. `GameEX::Startup` validates a complete dependency graph before side effects, computes a reproducible serial topological order, reverses that order for shutdown, and rolls back a subsystem whose own startup fails after partial acquisition. The real application now proves the boundary by showing and hiding its native window through an owned startup subsystem. The release also records the recovered Czech Republic data hierarchy and makes the WorldCompiler repository split a mandatory decision before heavy geospatial or machine-learning dependencies enter the supported build. The workspace builds warning-clean, all four tests pass, and strict Doxygen generation succeeds. Controlled parallel startup, rendering, world compilation, and data ingestion remain outside this version.

## Scope and aim

This version asks whether Game_EX can establish deterministic, reversible subsystem lifetime semantics before introducing worker concurrency. Its accepted deliverables are:

- an independently linked `GameEX::Startup` library with no platform, game, or compiler dependency;
- ordinary owned subsystem objects and stable dependency declarations, with no singleton/service lookup;
- rejection of invalid registrations, missing dependencies, and cycles before the first start call;
- deterministic serial topological startup and exact reverse shutdown;
- rollback that includes the currently failing partially started subsystem;
- protected single-use lifecycle states and cleanup that continues after an individual shutdown failure;
- meaningful integration with the application window lifecycle;
- unit, GUI smoke, strict-compiler, and Doxygen evidence;
- durable data-source precedence and a compiler repository split gate recovered from the earlier project discussion.

Parallel jobs, thread affinity, renderer startup, persistent world files, source ingestion, and editor visualisation are explicit exclusions.

## Design and implementation

`SubsystemRegistration` transfers a `std::unique_ptr<Subsystem>` together with a non-empty stable ID and dependency IDs into `StartupGraph`. The graph deliberately exposes no lookup API: collaborators remain constructor-injected and their ownership stays visible. Its lifecycle states distinguish configuration, startup, running, shutdown, successful completion, and terminal failure.

Validation builds an ID-to-entry map, resolves dependency references, and applies Kahn's topological algorithm. A sorted ready set selects the lexicographically smallest stable ID whenever more than one node is available. This produces the same serial order regardless of registration order while retaining true dependency ordering. Validation finishes before the graph enters `starting`, so structural errors leave it configurable and cause no subsystem call.

Each entry is appended to the attempted-start sequence immediately before `start()`. If that call throws after partial resource acquisition, reverse traversal therefore cleans the failing entry first and all previously started entries afterward. Normal shutdown uses the same reverse sequence. Cleanup attempts continue after a shutdown exception and the first exception is reported for explicit shutdown; rollback preserves the original startup exception. A single-use state machine prevents add/start/shutdown misuse, and the destructor performs non-throwing cleanup for a graph abandoned while running.

`Application` registers an adapter that treats window visibility as a reversible subsystem. The native window remains owned by `Application`, the graph is destroyed before it, and SDL remains isolated behind the platform implementation. [ADR 0006](../../decisions/0006-validated-serial-startup-graph.md) records this contract.

Three planning records constrain later work. The [data-source strategy](../../project/data-source-strategy.md) makes authoritative Czech Republic vector/terrain roles, ML semantics, EPSG:5514 precision, and inspect-before-combine behaviour explicit. [ADR 0005](../../decisions/0005-world-compiler-repository-split-gate.md) keeps the dependency-light compiler core in this repository but requires a split decision before GDAL, PROJ, Python/ML, network acquisition, or equivalent heavy dependencies are supported. [ADR 0007](../../decisions/0007-renderer-baselines-selection-and-parity.md) fixes OpenGL 4.6 Core, Vulkan 1.3, explicit/automatic selection behaviour, the developer toolchain, and the `v0.2.0` parity gate.

## Evidence and method

The release was assessed on Windows with MSVC 19.44 using:

```powershell
cmake --preset vs2022
cmake --build --preset debug
ctest --preset debug
cmake --build --preset docs
```

The Debug workspace build uses `/W4 /WX`. The final CTest run passed 4/4 tests in 0.80 seconds: `engine.startup_graph`, `world_format.header`, `game.window_smoke`, and `world_editor.window_smoke`. A standalone Engine configure/build/test also passed 1/1, confirming that `GameEX::Startup` and its tests do not depend on workspace composition. Doxygen covers production and test C++ code, is configured to turn warnings into errors, and completed without a warning. The rebuilt compiler banner reported application version `0.1.2` while retaining world-format version `0.1`.

## Data and assets

No external world data or asset is imported by this release. The data-source strategy names future products and recovered Bystřice bounds only as planning and acceptance metadata; it does not assert acquisition, licensing clearance, or redistribution. Existing pinned SDL3 source usage is unchanged.

## Discussion and reflection

Separating graph correctness from concurrency made lifecycle failure semantics observable before timing can obscure them. Recording a node before calling `start()` is a small but material choice: recording only successful calls would leak partial resources from the exact failure case rollback exists to handle.

The window adapter is intentionally narrow. It proves that this is application infrastructure rather than a test-only container while preserving main-thread platform work. It also exposes the requirement the next scheduler must retain: renderer and window work cannot be dispatched merely because a dependency node is ready.

Writing the data and split decisions alongside this foundation prevents later compiler convenience from silently choosing source authority, coordinate precision, repository topology, or dependency leakage. These are constraints on future code, not evidence that the data pipeline already exists.

## Limitations and risks

- Startup is serial and has no priority, affinity, cancellation, timeout, or progress-reporting model.
- Rollback preserves a startup exception but currently has no diagnostic channel for an additional cleanup exception.
- Lexical ID ordering is deterministic but could be mistaken for user-facing priority if IDs are chosen poorly.
- `Application` currently has only one window-visibility subsystem; renderer and world lifetimes have not yet exercised a larger production graph.
- The recorded source hierarchy still requires per-product licence and edition verification at acquisition time.
- The monorepository remains temporary beyond the dependency-light compiler core; the split gate must be resolved before heavy tooling is added.

## Next version

`v0.1.3` should add an ordinarily owned bounded job system and controlled parallel startup. It must keep a deterministic serial path, preserve full pre-validation, keep main-thread-affine nodes on the application thread, stop admitting new work after failure, wait for in-flight nodes, and define deterministic reverse rollback for nodes whose completions race. Its report should include controlled concurrency and failure tests rather than treating elapsed time alone as evidence.
