## Executive summary

Summarise the problem, the delivered result, the strongest acceptance evidence, and the most important remaining limitation. Write this after the work is complete.

## Scope and aim

State the question this version was intended to answer and why it mattered. List the accepted deliverables, explicit exclusions, success criteria, and any specification decisions obtained before implementation.

## Design and implementation

Explain the chosen design, dependency direction, ownership, important algorithms, and implementation boundaries. Link to source files, section documents, and ADRs rather than reproducing code or Doxygen API descriptions. Identify alternatives that materially affected the result.

## Evidence and method

Describe how the result was assessed. Include reproducible commands, test names, controlled inputs, hardware or platform details when relevant, and links to retained screenshots or logs. Separate measured output from visual observation and interpretation.

## Data and assets

For every input, identify its provider, product, source location, acquisition date, licence/attribution, redistribution status, geographic and temporal coverage, coordinate reference system, units, resolution, transformations, checksums, and whether it is raw, derived, sampled, generated, or project-authored. State explicitly when the version uses no external world data or assets.

## Results

Report the observed outcome against each success criterion. Include failures and unexpected results; do not turn plans into claims. Prefer small tables for repeated measurements and link to evidence retained in the repository.

## Discussion and reflection

Interpret the results. Explain what the version established, which assumptions held or failed, the consequences for architecture or workflow, and what would be done differently. Keep fact, inference, and recommendation distinguishable.

## Limitations and risks

Record known missing behaviour, representativeness limits, performance or portability gaps, technical debt, licence constraints, and unresolved specification questions. State the practical effect of each important limitation.

## Next version

Recommend the smallest next verifiable slice. Identify any specification gate that must be resolved first. A minor-version report also summarises the patch reports that contributed to its integrated capability.
